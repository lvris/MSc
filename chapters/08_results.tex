\subsection{An Example Run}\label{sec:eval:results:trace}

Before the numbers, we follow one task under two conditions. Task T1-01 starts with a booking for a party of eight that waits for a deposit. The goal text is ``Go ahead and confirm the booking.'' For a large party the site does not allow a plain confirmation. Paying the deposit is what confirms the booking (gate G1). In this state three operations are valid: \texttt{pay\_deposit}, \texttt{edit\_details} and \texttt{discard\_draft}.

\begin{enumerate}
    \item Under J, qwen3.5:9b sees all 21 operations. It first asks for the confirmation page, then calls \texttt{confirm\_booking}. The server refuses both. On the third step it calls \texttt{pay\_deposit}, which succeeds. Two of its three decisions are invalid.
    \item Under H, the same model sees the three controls of the current page, one of them ``Pay €80 deposit'', and returns that control's index. The task is done in one step, with no invalid decision.
\end{enumerate}

Both runs succeed. What differs is the path: under J the model finds out the state from the server's refusals; under H the state is already in what it is offered. The rest of this chapter counts this difference over all tasks and models.

\subsection{Invalid Actions by the Agent}\label{sec:results:agent}

This section answers RQ3 (a): does the agent try operations that the current state does not allow? As a reminder, the six conditions differ only in how the agent learns its actions (Section~\ref{sec:eval:method:conditions}). Table~\ref{tab:eval:invalid} gives the invalid action rate for every model and condition, and Table~\ref{tab:eval:invalid-kind} sorts the invalid actions by kind.

\subsubsection{Fixed action lists}\label{sec:eval:results:c1}

J, J+ and X give the agent the same kind of guide in three forms: a short list of operations (J), the list with a note on when each operation is allowed (J+), and the list as a standard MCP server (X). In all three the list does not change with the state, so the agent has to work out from the rules which operations it can use now. However the guide is written, the agent often gets this wrong and calls an operation that the current state does not allow: under J, J+ and X the invalid rate lies between 31.6\% and 82.1\% for every model (Table~\ref{tab:eval:invalid}).

A better guide does not fix this. The note in J+ helps qwen3.8-27b most (53.2\% to 31.8\%), qwen3.5:9b less (82.1\% to 72.0\%) and qwen3.5:4b not at all, and the MCP server in X moves the rate up for some models and down for others. All of them are real operations called in a state that does not allow them: the model knows the names, but not which ones are open now. Most of them (45\%) are pre-order operations called before the pre-order is open. Counting each repeated request only once makes the rates smaller but keeps the order of the conditions. qwen3.5:2b ends most episodes under J and J+ by stopping, usually at once, so its rates there rest on few decisions.

A more detailed guide or a standard protocol does not remove this kind of error, because the step it fails on, working out the current state from the rules, is still left to the agent.

\FloatBarrier

\subsubsection{Filtering by state}\label{sec:eval:results:c2}

If the problem is that the agent has to work out the current state, the obvious fix is to do that step for it and offer only the operations the current state allows. This removes most of the errors. But only one thing removes them by construction: letting the agent answer with the index of a control in the offered list, as under H, instead of naming an operation.

X+ is the same MCP server as X, with the tool list filtered by state, so from X to X+ only the filtering changes. The invalid rate drops to 0 for the three larger models and to 3.5\% for qwen3.5:2b. Most of the errors under the fixed lists therefore come from the state, not from the protocol. Filtering removes most of them, but not all.

\subsubsection{Choosing from the offered list}\label{sec:results:index}

The four errors left under X+ are all stale tools: qwen3.5:2b named a tool that the list had offered a few steps earlier and then withdrawn. Under X+ the agent answers with a tool name, which is free text, so it can still name a tool that is no longer on the list. Under H it answers with the index of a control on the current page, and no index points outside that list. Filtering decides what the agent is offered; answering by index decides what it can choose. The 0 under H therefore holds for every model, while the 0 under X+ holds only for the larger ones.

P reads the same page as H but lets the agent write the request itself. Here the result depends on the model: qwen3.5:4b and qwen3.8-27b make no invalid action, qwen3.5:2b is at 48.9\%. P is also the only condition with invented operations. We therefore do not claim that H is more accurate than P, only that its 0 does not depend on the model.

\subsection{Task Success}\label{sec:results:success}

Section~\ref{sec:results:index} showed that under H the agent never picks an invalid action. One may ask what this costs: keeping the agent to the controls on the current page might make some goals harder to reach. Task success shows that it does not. Success is only a secondary result here, because each cell has 24 tasks and one task moves the rate by about four points.

\subsubsection{Multi-step tasks}\label{sec:results:multistep}

The difference between the conditions is largest on T2 tasks, where the agent first has to reach another state before it can act. qwen3.8-27b succeeds on 7 of the 8 T2 tasks under H and on 3 under X+.

The random chooser separates what the constraint does from what the model does. With no model at all, its success rises from 16.7\% under J to 37.5\% under H. Nearly all of this comes from T1 tasks, where one valid action is enough: on T2 it succeeds on at most 2 of 8 tasks in any condition. The constraint keeps the agent on valid actions, but a goal that needs several steps still needs a model.

\subsubsection{Unreachable goals}\label{sec:results:unreachable}

Under H every failure is a sequence of valid actions, such as cancelling a booking the user believed was unfinished. \subsection{Controls Shown to the User}\label{sec:results:interface}

This section answers RQ3 (b): when the model builds the interface the user sees, does it show controls the user cannot use? The data come from the interface audit (Section~\ref{sec:eval:method:audit}), run with qwen3.5:9b and qwen3.8-27b.

Section~\ref{sec:results:agent} showed that an agent working from an unfiltered list often picks an operation the current state does not allow. On the interface side the same problem reaches the user. When the model builds the screen from an unfiltered list, it shows operations that cannot be used now, and the user sees dead controls (buttons and forms that do nothing when used). Filtering by state removes the dead controls, but under X+ the interface still asks the user again for values the page already has, and adds fields the operation does not have. H does neither, because each control on the page carries its own values.

\subsubsection{Dead controls}\label{sec:results:dead}

Without a model, the size of the problem is easy to state. If the full list of operations is drawn as an interface, 87.9\% of its controls are dead, counted over all 997 reachable states; under H the share is 0 by construction. A model does better than this, because it leaves out some of the operations that do not fit. It does not leave out all of them. Under J and J+, 13.8\% and 15.4\% of the controls qwen3.8-27b shows are dead, and 47.5\% and 39.4\% of those qwen3.5:9b shows. Under J, half of the qwen3.5:9b screens contain at least one dead control. The dead controls fall in the same places as the invalid actions of the agent: adding a dish before the pre-order is open, cancelling a booking inside the 24-hour window, confirming a large party without the deposit. The model does not know the current state, and the interface shows it.

\subsubsection{Values that come with the control}\label{sec:results:values}

Under X+ and H no control is dead. The two still differ in what the user is asked to fill in. Under J, J+ and X+ both models ask the user again for the date and the party size, which the user has already chosen on the page (5 to 6 fields per condition and model). Under H this never happens, because a control on the page carries such values with it. Over all 997 states, 58\% of the fields of the page's controls already have a value, either fixed by the control (23\%) or prefilled (35\%). The fixed list declares the same 1\,443 fields but carries a value for none of them. Our X+ server adds the allowed values of a parameter, but not the value the current state has already fixed. A server could add these too, but it would have to repeat in its schema what the page already states. What H leaves to the user is the name, phone, card and reason, which only the user knows.

X+ also adds fields that the operation does not declare: two for qwen3.8-27b, five for qwen3.5:9b, for example a card number, expiry date and CVV where the deposit operation takes a single card field. Under H the renderer draws exactly the declared fields, so the model cannot add any.

Filtering gives the interface the right controls. Only the page gives it the right controls together with their values.

The first cost is the work on the site side. Under H the agent reads the page the site already serves to people, so nothing extra has to be written. X+ reaches the same invalid rate for the larger models, but only because the site runs a separate MCP server that filters its tools by state. That server has to be kept consistent with the page: every rule the page applies has to be written again in the server, and when one changes, the other has to change too. The same holds for the interface: under H the renderer turns the page's controls into an interface without a model call (Section~\ref{sec:impl:ui}); the model only picks which controls to show.

The second cost is tokens (Table~\ref{tab:eval:tokens}). H and X+ use the fewest. The fixed lists J, J+ and X use about five to ten times as many as H for qwen3.5:4b and qwen3.5:9b, and two to four times as many for qwen3.8-27b. Two things add up. Each step's prompt is larger, because a fixed list describes all 21 operations: about 300 to 400 prompt tokens per step under H, 600 under X+ and 2\,000 under X. And the agent takes more steps, because every refused call costs a step: qwen3.5:9b takes 5.1 steps per episode under J and 1.7 under H.

Few steps do not always mean an efficient agent. qwen3.5:2b takes few steps under J, J+ and H because it mostly stops at once (Section~\ref{sec:results:success}). It is expensive under P because it writes long outputs when it builds requests from the raw page, about 3\,000 completion tokens per step, and under X because it gets stuck and repeats refused calls.

For RQ3 (a), an agent that gets a fixed list of operations often calls one the current state does not allow, however the list is written. Filtering the list by state removes most of these errors. Only answering with the index of a control on the current page removes all of them, for every model. Keeping the agent to these controls does not lower its success, and for the three larger models it tends to raise it.

For RQ3 (b), the same holds for the interface the user sees. Built from a fixed list, it shows dead controls. Built from a filtered list, it shows the right controls, but asks the user again for values the page already has and adds fields that do not exist. Built from the page's controls, it shows the right controls with their values, and its zeros do not depend on the model.

Using the page needs no second interface, and its token cost is as low as that of the filtered server. What the constraint does not do is choose the right action among the valid ones: on goals that cannot be reached, every condition sometimes changes the booking. Chapter~\ref{sec:discussion} discusses what these results mean for the authors of applications and agents, and where their limits are.
