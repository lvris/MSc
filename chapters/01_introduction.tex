The web was built for people: its pages are written to be read, and its links and forms to be followed and filled in by hand.
Software agents built on large language models now also act on these pages on a person's behalf, booking tables, buying tickets and ordering goods \cite{yang2025agentic, ning2025survey}.
At the same time, the way people work with such assistants is changing: instead of answering only in text, an assistant increasingly generates buttons and forms for the user to act on \cite{googleGenUI2025, openaiApps2025}.
This raises a question that neither the agent nor the generated interface can answer on its own: which actions are possible right now, and who decides?

\subsection{Motivation}\label{sec:intro:motivation}

% agent 已经改变了人们的生活, 除了传统的搜索和问答, 还可以在网页上执行操作, 例如订餐、预定机票、购买商品等.
% 然而, 想象一下在一个餐厅中, 你想预定一张大桌子, 但是餐厅要求你先支付 80 欧元的定金, 然后才能确认预订.
% agent 在这种情况下可能会遇到问题: 它可能会尝试直接确认预订, 但是由于没有支付定金而被拒绝.
% 而网站自己的页面只提供「付定金 / 修改 / 放弃」选项. 这说明了纯对话式界面在处理复杂、状态依赖的网页任务时存在认知负荷和效率低下的问题.

Consider a restaurant booking site.
A party of eight has entered its details, and because the party is larger than six, the restaurant requires a deposit of \texteuro{}80 before the booking can be confirmed.
The user tells an agent to go ahead and confirm the booking.
\autoref{fig:intro:motivation} shows three ways this can go.

An agent given the full list of the operations of the site finds \texttt{confirm\_booking} on it and calls it, and the site refuses, because the deposit has not been paid (a).
If the same list is drawn as an interface for the user, the user sees a button to confirm the booking that does nothing when pressed, next to many others that do nothing either (b).
The page of the site itself, by contrast, shows only the three controls that work in this state: pay the deposit, edit the details, or discard the draft (c).

(b) An interface drawn from the same list shows controls that do nothing in this state. (c) The page of the site shows only the controls that work now.}

Whether an action can be taken depends on the current state, and the site already knows this: its page shows exactly the actions that are possible now.
That page is also the interface people already use.
This thesis argues, and tests, that the same page can serve the agent and the generated interface as well, so that both are limited to the actions the site offers in its current state.

    \item[] \textbf{RQ3:} In a simulated booking site, when actions are limited to the controls on the current page, how often (a) does the agent try an action it cannot take, and (b) does the generated interface show a control the user cannot use, compared with other ways of giving the model its actions?

\subsection{Contributions}\label{sec:intro:contrib}

This thesis makes four contributions.
\begin{enumerate}
    \item A comparison of existing systems by where their set of actions comes from, including interfaces built specifically for agents (\autoref{sec:bg:frameworks}, RQ1).
    None of them produces the action set from the application itself, follows the current state, and shares the interface people use, all at once.
    \item A framework that takes the controls on the current page as the set of actions of the current state, states the contract a site must meet for this set to be exactly the valid actions, and gives the set two consumers: the agent, which executes from it, and the interface, which is drawn from it (\autoref{sec:design}, RQ2).
    \item A prototype consisting of a generic client with no code specific to any site, a restaurant booking site, and a renderer that draws the interface without calling a model (\autoref{sec:impl:prototype}, RQ2).
    \item An evaluation with two experiments, one on the actions of the agent and one on the generated interfaces, across six conditions that include a real MCP server, with tasks derived from the state machine of the site and an independent judge that does not read its internal state (\autoref{sec:eval:method:conditions}, \autoref{sec:results}, RQ3).
\end{enumerate}

With a fixed list of operations, the agent often tries actions that the current state does not allow, and an interface drawn from that list shows controls that do nothing.
Choosing from the controls on the current page removed these errors for every model tested (\autoref{sec:results:summary}).

\subsection{Scope}\label{sec:intro:scope}

This thesis measures only whether actions are valid.
There is no user study, so the usability, appearance and completion time of the generated interfaces are not evaluated (\autoref{sec:disc:threats}).
The experiments use one synthetic site, for the reasons given in \autoref{sec:methods:synthetic}.
The approach covers sites whose controls are present in the HTML that the server returns; many real sites produce their controls only by running JavaScript \cite{fouquet2023breaking}, and these are outside the scope (\autoref{sec:design:site-contract}).
Security is not addressed, although an agent that reads web pages can be attacked through instructions hidden in them \cite{greshake2023not}.
Finally, the constraint keeps the agent to actions that can be done, but it cannot tell which of them the user wants.
