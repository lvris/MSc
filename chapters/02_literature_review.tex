Software agents built on large language models can now operate the web on a person's behalf, and the interfaces through which people direct them are being redesigned around that fact.
This chapter discusses how agents increasingly meet their users through generated interfaces.
Existing frameworks for such interfaces are reviewed, the question of what grounds the actions they offer is raised, and HTML hypermedia is proposed as a solution.
In doing so, the chapter answers RQ1 (\autoref{sec:intro:rq}): how existing systems decide which actions an agent may take and which controls a generated interface shows, and what is missing.
The sources were found by a targeted search for the closest related work, extended by following references backwards and forwards \cite{wohlin2014guidelines}.
Product documentation and protocol specifications are included alongside papers, because many of the systems are described only there.

\autoref{sec:bg:internet} traces how the web came to be read by machines as well as by people, and \autoref{sec:bg:genui} how agents came to meet their users through generated interfaces.
\autoref{sec:bg:hypermedia} introduces hypermedia and the notions of state and affordance on which the comparison relies.
\autoref{sec:bg:frameworks} compares existing systems by where their actions come from, \autoref{sec:bg:rendering} covers the frameworks that draw generated interfaces, and \autoref{sec:bg:gap} states what is missing.

\subsection{Internet, Human, and Machine}\label{sec:bg:internet}

Web interaction evolved from pages authored for human reading toward pages that non-human clients also need to act on.
The earliest such clients like web crawlers only read while later ones increasingly act: scripted automation at first, and most recently LLM-based agents that follow links, fill forms, and complete transactions on the user's behalf \cite{mesbah2012crawling, ning2025survey, yang2025agentic}.


Because pages are written for humans, a machine client has no direct access to application meaning: it must recover what a page is, and what can currently be done with it, from artifacts intended for human perception, such as markup structure, layout and visible text.
This recovery is indirect and brittle, and the difficulty motivated a long line of work on giving the web machine-readable semantics, most prominently the Semantic Web programme and its lighter-weight descendants such as embedded structured annotations \cite{berners-lee2001semantic, guha2016schemaorg}.
% https://arxiv.org/html/2507.10644v1#bib.bib87 may be useful for the semantic-web citation

The semantic-web approach asked authors to maintain a second, machine-facing representation of their application in parallel with the human-facing page.
Annotations that are not needed to render the page for people are exercised by nothing the author depends on, and so they are the first thing to fall out of date.
Descriptions maintained apart from the implementation are known to go out of date and to disagree with what they describe \cite{uddin2015how, mastouri2026rest}.

\subsection{From Conversational Agents to Generative UI}\label{sec:bg:genui}

Large language models came from the other side: they made machines better readers of pages written for humans.
Their first and still dominant form is conversational.
Chat interfaces in the ChatGPT style proved capable at open-ended language tasks, and they inherit a long lineage of conversational-interface research \cite{mctear2017rise}.

These models were then given the ability to act with scaffolding for planning, tool use, and memory, they can call tools, operate websites, and carry out multi-step tasks against external systems, and an ecosystem of such agents has grown around the web in particular \cite{yang2025agentic, ning2025survey, zhou2024webarena, gur2023realworld, song2025browsing}.
How a person should work with such an agent then became an open question.

For these richer, structured, stateful tasks, pure conversation shows limits:
\begin{enumerate}
    \item \textbf{Lossy communication:} natural language is a lossy, serial channel for what are really structured choices: selecting one of many flights, configuring a filter, or filling a constrained form is painful to conduct sentence by sentence.
    \item \textbf{Hidden action space:} narrating actions hides the actual action space from the human, who cannot see what the agent could have done, verify what it actually did, or take over precisely \cite{zhang2025exploring}.
\end{enumerate}

Generative UI responds to these limits: besides text, the agent renders controls, forms and choices fitted to the current step of the task \cite{leviathan2025generative, aisdkGUI}.
The industry is already moving this way: mainstream assistants increasingly wrap their responses in generated widgets and forms even outside web-operation tasks, as Gemini does with its generated interfaces and ChatGPT with interactive apps inside the conversation \cite{googleGenUI2025, openaiApps2025}, which corroborates that pure text is insufficient as an interaction surface.

This thesis looks at one case of this: generated controls that correspond to real actions on an external application with state.
For such controls the main question is whether each one exists and can be used now.
The rest of this chapter is organized around that problem.
Because the surface is produced by a model, and models are known to generate content that is not supported by their input \cite{ji2023survey}, a generated surface can present controls that are invalid, stale, or outright hallucinated relative to what the application can actually do at this moment.

\subsection{HTML Hypermedia, State, and Affordances}\label{sec:bg:hypermedia}

\subsubsection{REST and the hypermedia constraint}

Hypermedia denotes representations that carry both content and the controls for moving to other application states \cite{hypermediaBook}.
In HTML those controls are links, forms, and buttons, and in server-driven variants such as htmx, attributes that declare further exchanges with the server \cite{htmxlDocs}.
Hypermedia formats aimed only at machines also exist, such as the JSON-based HAL and Siren, but HTML is the one that matters here, for a reason this section builds toward: it is the only widely deployed hypermedia format whose representations are at the same time a human interface.

This is not a new idea but the original architecture of the web.
Fielding's REST names the principle hypermedia as the engine of application state: transitions should be driven by controls that the server places in the current representation, not by out-of-band contracts the client holds separately \cite{fielding2000architectural, hypermediaBook}.
WSDL and OpenAPI were the out-of-band contracts of their eras \cite{wsdl2001, openapi2021}.

The controls in a representation can be read as its affordances: the state-dependent set of actions the application currently makes available \cite{gidey2025affordance}.
The term is used here in the hypermedia community's sense \cite{hypermediaBook}.

Read against \autoref{sec:bg:frameworks}, this identifies the pattern that MCP repeats.

\subsubsection{Consequences}

This thesis builds on one observation.
In a hypermedia application, the HTML the server returns is one artifact playing three roles at once: the interface the human sees, the action space an agent can parse, and the set of controls through which the application is actually operated.
Because one document fills all three roles, they cannot drift apart.
An agent that takes those controls as its source of valid actions reads the same controls the person is given, without guessing from the DOM or relying on a separately maintained description.
A separately maintained contract, however well specified, lacks this property by definition.

\begin{enumerate}
    \item \textbf{No drift:} the affordance description comes with building the application and needs no second artifact, so the problem of \autoref{sec:bg:internet}, a description that nothing depends on, does not arise.
    \item \textbf{Native state-dependence:} the page describes the current state and the ways out of it, and nothing more.
    \item \textbf{Graceful fallback:} when the agent fails, the human can operate the same page directly.
    Early evidence that machine-legible interfaces improve agent reliability is consistent with this picture \cite{schultze2025building}.
\end{enumerate}

\begin{oldtext}
A separate contract such as MCP cannot offer this property, however well specified, because separateness is exactly what the property excludes.
\end{oldtext}

\subsubsection{Rendering-side vs. Source-side}

Two concerns run through this loop and are worth separating, because existing systems tend to address only one of them.
The rendering side concerns how agent output is drawn for the human.
The action-source side concerns where the set of actions the agent may take, and may offer, comes from.
The two are independent; the rest of this section groups systems by the second, and \autoref{sec:bg:rendering} covers the first.

\subsubsection{Inference from the page}\label{sec:bg:inference}

The weakest grounding is inference from the live page.
Browser and computer-use agents recover their action set from the DOM, the accessibility tree, or screenshots, and realistic web tasks remain difficult and brittle when the agent must guess in this way what a page affords \cite{zhou2024webarena, song2025browsing}.
% This is the indirect-recovery problem of \autoref{sec:bg:internet} replayed with a stronger model.
Magentic-UI keeps a human in the loop through co-planning and approval of actions, but the actions it proposes are still inferred from the page the browser shows \cite{mozannar2025magenticui}.
Even picking out the right element from a whole page is hard: on Mind2Web, first narrowing the raw HTML down with a small model clearly improved the choices of a larger one \cite{deng2023mind2web}.

\subsubsection{Registration at build time}\label{sec:bg:registry}

A stronger answer registers the actions on the client at build time: the developer declares a set of tools or components that the model may invoke, explicit and typed \cite{aisdkGUI}.
This grounds the vocabulary but not the state.
The registry is static and application-specific, and nothing prevents it from drifting away from what the backend currently allows.

\subsubsection{A separate machine interface}\label{sec:bg:mcp}

The strongest existing answer is a server-declared contract, and its current form is the Model Context Protocol (MCP).
MCP goes far in this direction: the contract is machine-readable, owned by the server rather than assumed by the client, gives every tool a typed input schema, and can update the tool list at runtime \cite{mcpSpec2025}.
Read against \autoref{sec:bg:hypermedia}, however, a tool catalog obtained at connection time is the same kind of client-held description as WSDL and OpenAPI, separate from the representation the application actually serves.

Two limits remain.
First, the specification lets a server announce that its tool list has changed, through the \texttt{listChanged} capability, but says nothing about tools appearing or disappearing with the state of the application \cite{mcpSpec2025}.
A tool list that follows the state is therefore allowed but not expected, and a server that does not filter offers every tool in every state.
Second, the contract is a second description, maintained beside the interface people use, and so it can drift from the application in the way described in \autoref{sec:bg:internet}.
When MCP servers are generated from existing OpenAPI descriptions, every fault found in the generated tools traces back to an inconsistency or omission in those descriptions \cite{mastouri2026rest}.

\citet{jiang2026web} argue in the same direction for the web as a whole: instead of clicking through pages, an agent should call typed \emph{verbs}, functions with structured inputs and outputs that may carry preconditions, backed by a server-side API or by a maintained client-side workflow.
The verbs are exposed by the website or written by third parties, and the agent interacts only with the verb interface, never with the page.
Such verbs are again a layer beside the page, and the authors place the cost of keeping them working on the site developer or another maintainer.

\paragraph{The closest comparison.}
The work closest to this comparison is that of \citet{steiner2025mcp}, who give the same set of shops four interfaces, HTML, retrieval (RAG), MCP and NLWeb, and run the same agent tasks against each.
The HTML agent did worst: averaged over all tasks, its F1 score was 0.67 against 0.75--0.77 for the others, and it used about 241k tokens per task against 47k--140k.
Their HTML agent, however, observes the accessibility tree of each page and infers what to click and fill, so it belongs to the first group above.
The study measures effectiveness and cost, and does not check whether a proposed action was valid in the current state.

\subsubsection{Agent-native interfaces}\label{sec:bg:agent-native}

A fourth group, agent-native interfaces, gives up on the human interface and builds a separate one for the agent.
AXIS lets an agent call application APIs where they exist and falls back to the GUI, exploring the application to build those APIs \cite{lu2025axis}.
UFO2 combines GUI actions with native APIs on Windows \cite{zhang2025ufo2}, and OS-Copilot operates the whole operating system through one unified interface \cite{wu2024oscopilot}.
GOI takes navigation and interaction off the model and leaves it only the semantic decisions \cite{wang2026imperative}, and CLI-Anything generates command-line interfaces for existing software \cite{cliAnything}.
DynaSaur goes the opposite way: instead of choosing from a fixed set, the agent writes its own actions as code \cite{nguyen2025dynasaur}.
Early evidence suggests that interfaces built to be legible to machines do make agents more reliable \cite{schultze2025building}, and this group is the most direct answer to the guessing of the first.

\paragraph{ASIL.}
ASIL is the most complete of these systems \cite{xie2026asil}.
It starts from the observation that screenshots are state-incomplete and GUI actions brittle, and gives the agent a structured observation of the application together with actions that are checked for validity before they run.
It differs from the approach of this thesis in three ways.
First, the action set is produced by an adapter written for each application, and the authors list access-path discovery, application-specific bridges, GUI synchronisation and task design as manual work.
Second, the interface is for the agent only, and showing the person what the agent sees requires a separate synchronisation with the GUI.
Third, its evaluation measures task success and does not check whether the actions offered or attempted were valid.

\subsection{Generative-UI Rendering Frameworks}\label{sec:bg:rendering}

AG-UI defines an event and transport protocol between agents and front ends \cite{aguiOverview}, Vercel's AI SDK maps model output to registered interface components \cite{aisdkGUI}, and CopilotKit embeds agent interaction into existing applications \cite{copilotkitDocs}.
These systems are complementary to this thesis: they deal with how a generated surface is drawn and leave open which controls it may contain, and they could sit on top of the framework developed here.

\subsection{Research Gap}\label{sec:bg:gap}

\autoref{tab:bg:comparison} shows what is missing.
For the controls of a generated interface to be trusted, three things must hold at once.
The application itself produces the action set, with no guessing by the agent, no adapter and no second description.
It contains only the actions that are valid in the current state.
It is the same artifact as the interface the person uses.
Page inference has the third property but guesses its actions.
An MCP server that filters its tools by state, or an agent-native interface such as ASIL, can have the second, but neither has the first or the third.
No existing system therefore binds a human-facing generated interface to an action set that the application itself produces for its current state.
The evaluations reviewed here also measure task success and cost; none checks whether a generated interface offers controls that cannot be used.

\begin{oldtext}
Web agents can operate human-facing sites, but they infer their actions from artifacts made for human perception, and the inference is brittle.
Generative-UI frameworks can render dynamic surfaces, but they ground the actions those surfaces expose weakly: inferred from the page, fixed at build time, or delegated to a machine-only contract that runs parallel to the human interface and can drift from it.
No existing framework binds a human-facing generated surface to a state-dependent, server-authoritative action set.
\end{oldtext}

This thesis responds by using HTML hypermedia affordances as that binding layer: the generated interface is constrained to the controls the server placed in the current representation, so every action it offers is currently valid.
This is also what the title means by deterministic.
The determinism concerns the action space: the set of actions that can be offered depends only on the state of the server, and model sampling does not change it; every offered control exists and is executable at the moment it is shown; every refusal is structural.
The agent's selection among valid actions remains stochastic, and no stronger claim is made.
\autoref{sec:implementation} defines this property and builds the framework that realizes it.
